# TicketHub — Event Ticketing System Design

## 1. Requirements

### 1.1 Functional Requirements

TicketHub is a web application that allows users to discover events, select seats, purchase tickets, and access their purchased tickets.

The system must support the following features:

1. **User management:** Users can register, sign in, and manage their accounts.
2. **Event browsing:** Users can browse upcoming events, search by name or location, and view event details, prices, dates, and venues.
3. **Seat availability:** Users can view a seating map and see which seats are available, temporarily held, or sold.
4. **Seat holding:** Users can temporarily reserve available seats while completing checkout.
5. **Payment processing:** Users can pay for held seats through a payment provider.
6. **Order management:** Users can view order details, payment status, and purchase history.
7. **Ticket delivery:** After successful payment, the system issues tickets with unique identifiers or QR codes.
8. **Order expiration:** Unpaid seat holds expire automatically so that seats can become available again.
9. **Fair access:** During popular ticket sales, users enter a controlled queue to reduce overload and give eligible customers an orderly opportunity to purchase.
10. **Administration:** Authorized staff can create events, configure seating, set prices, and monitor sales.

### 1.2 Non-Functional Requirements

**Performance**
- Event listings should load within 2 seconds at the 95th percentile under normal traffic.
- Seat availability and checkout requests should generally complete within 2 seconds, excluding external payment processing.
- The system should scale horizontally during major ticket releases.

**Correctness and consistency**
- A seat must never have more than one confirmed sale for the same event.
- Seat holds must be atomic: a seat is held for one user only if it is still available.
- An order must not be marked paid until the payment provider confirms the payment.
- Duplicate payment notifications and repeated requests must not issue duplicate tickets.

**Availability and reliability**
- Target 99.9% monthly availability, excluding agreed maintenance.
- Failed operations should not leave seats permanently held.
- The system should recover from application-server failures without losing confirmed orders.

**Fairness**
- A virtual waiting room should control the number of customers entering the purchase flow.
- Queue positions should be assigned consistently, with clear rules for priority access if applicable.
- Seat holds should have a fixed expiration period, such as five minutes.
- Users should see accurate availability and clear messages when seats become unavailable.

**Security**
- Authentication and role-based authorization protect user accounts and administrative functions.
- All traffic uses HTTPS.
- Payment card details are handled by a compliant payment provider rather than stored directly by TicketHub.
- Rate limits, input validation, and abuse detection protect APIs from automated attacks.

**Scalability**
- The system should support 2 million registered users and bursts of traffic substantially above normal levels.
- Browsing traffic should be handled separately from the more sensitive seat-holding and payment operations.

## 2. Traffic and Capacity Estimates

### 2.1 Assumptions

- Registered users: 2,000,000.
- Normal daily visitors: 50,000.
- Pages viewed per visitor: 10.
- Normal daily ticket sales: 5,000.
- Popular sale audience: 200,000 people attempting to purchase 20,000 seats in 10 minutes.
- One day is approximated as 100,000 seconds for quick estimates.
- For peak estimates, the actual 10-minute sale window is 600 seconds.
- These estimates exclude additional API requests generated by each page and seat-map polling.

### 2.2 Normal Traffic

**Daily page views**

50,000 visitors × 10 pages = 500,000 page views per day.

**Average page requests per second**

500,000 ÷ 100,000 ≈ 5 requests per second.

Using the actual 86,400 seconds in a day gives approximately 5.8 page views per second.

For planning, assume a normal peak of five times the daily average:

5 × 5.8 ≈ 29 page views per second.

**Average ticket sales**

5,000 ÷ 86,400 ≈ 0.058 tickets per second.

This is approximately 208 tickets per hour on average.

Ticket purchases are not evenly distributed throughout the day, so checkout capacity must be higher than this average.

### 2.3 Popular Concert Sale

**Attempted buyers per second**

200,000 ÷ 600 ≈ 333 people per second.

**Seats available per second, on average**

20,000 ÷ 600 ≈ 33 seats per second.

**Competition for tickets**

200,000 potential buyers ÷ 20,000 seats = 10 potential buyers per seat.

Only 10% of the audience can obtain a seat if all seats are sold to distinct buyers and every seat is purchased.

The average buyer arrival rate is approximately 333 per second, but the actual peak may be much higher if users arrive simultaneously when sales open.

### 2.4 Comparison

| Metric | Normal day | Popular sale |
|---|---:|---:|
| Daily visitors or sale audience | 50,000 | 200,000 in 10 minutes |
| Page views | 500,000 per day | Depends on browsing and retry behavior |
| Average page-view rate | 5.8 per second | Not specified by the supplied facts |
| Buyer arrival rate | Not specified; 5,000 daily sales | 333 per second |
| Tickets available | 5,000 sold per day | 20,000 seats |
| Main risk | Routine availability and latency | Overload, unfair access, and seat contention |

The big sale cannot be sized using the normal daily average alone. TicketHub needs a waiting room, horizontal scaling, caching for read-heavy endpoints, and strict concurrency control on seat reservations.

The 333 buyers per second figure is an average arrival rate, not a guaranteed peak API request rate. A single buyer may generate multiple requests, so load testing must measure actual request volume and burst behavior.

## 3. API Design

The API uses HTTPS and JSON. Authenticated endpoints require a valid session or access token. Each request that can create an order or trigger a payment must support idempotency where appropriate.

### 3.1 Endpoints

| Method and endpoint | Purpose | Important behavior |
|---|---|---|
| `GET /api/events` | Browse and search events | Supports pagination and filters |
| `GET /api/events/{eventId}` | View event details | Returns venue, date, and event information |
| `GET /api/events/{eventId}/seats` | View seats and availability | Returns seat identifiers, prices, and current status |
| `POST /api/events/{eventId}/holds` | Hold selected seats | Atomically reserves seats for the authenticated user |
| `GET /api/holds/{holdId}` | Check hold status | Returns expiration time and current status |
| `DELETE /api/holds/{holdId}` | Release a hold | Releases seats only if the hold is still active |
| `POST /api/orders` | Create an order from a valid hold | Rejects expired or invalid holds |
| `POST /api/orders/{orderId}/payment` | Initiate payment | Uses a payment provider and an idempotency key |
| `POST /api/payments/webhook` | Receive payment notifications | Verifies the provider signature and processes events idempotently |
| `GET /api/me/tickets` | View the user's tickets | Returns only tickets owned by the authenticated user |

### 3.2 Example: Hold Seats

Request:

`POST /api/events/101/holds`

```json
{
  "seat_ids": [501, 502]
}
```

Successful response:

```json
{
  "hold_id": "hold-abc123",
  "status": "ACTIVE",
  "expires_at": "2026-10-27T12:05:00Z",
  "seat_ids": [501, 502]
}
```

If either seat is unavailable, the system should reject the request without partially holding the requested seats.

A conflict response can use HTTP `409 Conflict` and explain that one or more selected seats are no longer available.

### 3.3 Example: Browse Events

`GET /api/events?page=1&limit=20`

The response contains event summaries and pagination information. Frequently accessed event details can be cached because they change less frequently than seat availability.

### 3.4 API Safety

- Authenticate requests that create holds, orders, or tickets.
- Verify that the user owns the hold before allowing checkout or release.
- Apply rate limits to browsing and purchasing endpoints.
- Use idempotency keys to prevent repeated client requests from creating duplicate orders or payment operations.
- Treat payment-provider webhooks as untrusted until their signatures are verified.
- Never rely on client-side seat availability as the final authority; the database must verify availability when the hold is created.

## 4. Data Model

TicketHub uses a relational database such as PostgreSQL because ticket purchasing requires transactions, foreign keys, and uniqueness constraints.

### 4.1 Tables

#### Users

| Column | Type | Description |
|---|---|---|
| `id` | UUID, primary key | Unique user identifier |
| `email` | VARCHAR, unique | Login email |
| `password_hash` | VARCHAR | Secure password hash |
| `created_at` | TIMESTAMP | Account creation time |

#### Events

| Column | Type | Description |
|---|---|---|
| `id` | UUID, primary key | Unique event identifier |
| `name` | VARCHAR | Event name |
| `venue` | VARCHAR | Venue name |
| `starts_at` | TIMESTAMP | Event start time |
| `status` | VARCHAR | Draft, published, or cancelled |

#### Seats

Each row represents a physical seat for a specific event.

| Column | Type | Description |
|---|---|---|
| `id` | UUID, primary key | Unique event-seat identifier |
| `event_id` | UUID, foreign key | References `Events.id` |
| `section` | VARCHAR | Seating section |
| `row_label` | VARCHAR | Row identifier |
| `seat_number` | VARCHAR | Seat identifier within the row |
| `price` | DECIMAL | Ticket price |
| `status` | VARCHAR | Available, held, or sold |

Constraint: `UNIQUE (event_id, section, row_label, seat_number)` prevents duplicate definitions of the same physical seat within an event.

#### Orders

| Column | Type | Description |
|---|---|---|
| `id` | UUID, primary key | Unique order identifier |
| `user_id` | UUID, foreign key | References `Users.id` |
| `status` | VARCHAR | Pending, paid, cancelled, or failed |
| `total_amount` | DECIMAL | Total order amount |
| `idempotency_key` | VARCHAR | Unique key for safe retries |
| `created_at` | TIMESTAMP | Order creation time |

Constraint: `UNIQUE (user_id, idempotency_key)` prevents repeated requests from creating duplicate orders for the same user and key.

#### Seat Holds

| Column | Type | Description |
|---|---|---|
| `id` | UUID, primary key | Unique hold identifier |
| `user_id` | UUID, foreign key | References `Users.id` |
| `expires_at` | TIMESTAMP | Hold expiration time |
| `status` | VARCHAR | Active, converted, expired, or released |
| `created_at` | TIMESTAMP | Hold creation time |

#### Order Items

| Column | Type | Description |
|---|---|---|
| `id` | UUID, primary key | Unique order-item identifier |
| `order_id` | UUID, foreign key | References `Orders.id` |
| `seat_id` | UUID, foreign key | References `Seats.id` |
| `price_at_purchase` | DECIMAL | Price captured at checkout |

Constraint: `UNIQUE (seat_id)` in the order-items table is a simple way to prevent a seat from appearing in more than one order item, provided cancelled or refunded sales do not reuse the same row. For a production system that allows resale or cancelled orders, use a separate ticket allocation or sales-history design and enforce uniqueness only for active or confirmed allocations.

#### Tickets

| Column | Type | Description |
|---|---|---|
| `id` | UUID, primary key | Unique ticket identifier |
| `order_item_id` | UUID, unique foreign key | References `OrderItems.id` |
| `ticket_code` | VARCHAR, unique | Unique ticket or QR-code identifier |
| `issued_at` | TIMESTAMP | Ticket issuance time |
| `status` | VARCHAR | Valid, cancelled, or used |

### 4.2 Relationships

- One user can create many orders.
- One event has many seats.
- One user can create many seat holds.
- One order has many order items.
- Each order item references one seat.
- Each order item can have one issued ticket.
- A hold can cover multiple seats; in a normalized implementation, use a `Hold Items` table with one row per held seat.

The seat-hold items should reference both the hold and the seat. Database constraints and transactional allocation logic must ensure that one seat cannot have two active holds.

## 5. Preventing Double-Booking

Double-booking is one of the most important correctness problems in TicketHub. Two customers may request the same seat at nearly the same time. Checking availability in the application and then updating it later is unsafe because both requests could observe the seat as available.

TicketHub uses database transactions, row-level locks, and uniqueness constraints.

### 5.1 Atomic Seat-Hold Process

1. The user selects seats and submits a hold request.
2. The application starts a database transaction.
3. It locks the requested seat rows using `SELECT ... FOR UPDATE`, in a consistent seat-ID order to reduce deadlocks.
4. It verifies that every requested seat is available and has no unexpired hold.
5. It creates the hold and the associated hold-item rows.
6. It marks the seats as held, or records their active allocation in the hold-item table.
7. It commits the transaction.

If any requested seat is unavailable, the transaction rolls back and none of the requested seats are held.

When two requests target the same seat, the database lock serializes their access. The second request waits, then observes the committed allocation and fails instead of reserving the same seat.

### 5.2 Constraints and Hold Expiration

The application must enforce database constraints that prevent duplicate active seat allocations. One approach is to store active allocations in a dedicated table with one row per currently allocated seat and a unique constraint on `seat_id`. When a hold expires or is released, its active allocation is removed transactionally. Historical holds can remain in the holds tables for auditing.

Expiration must be handled safely: a background worker can identify expired holds, but the transaction that attempts a new hold must also verify expiration. Correctness must not depend on the cleanup worker running exactly on time.

### 5.3 Payment and Order Confirmation

The system must not keep a database transaction open while waiting for an external payment provider.

Instead:

1. Create a pending order from a valid hold.
2. Initiate payment with the provider using an idempotency key.
3. Receive and verify the payment result or webhook.
4. In a database transaction, confirm the order, convert the active seat allocations into confirmed sales, and issue tickets exactly once.
5. If payment fails or the hold expires, release the allocation according to a clearly defined payment-reconciliation policy.

The system must handle late payment confirmations carefully. If a payment succeeds after a hold has expired and the seat has been sold to someone else, TicketHub must not confirm a second sale. It should reconcile the payment and refund or otherwise resolve the failed allocation.

This design protects correctness at the database boundary rather than relying on fast application code or the user interface.

### 6.2 Component Responsibilities

**CDN and Web Application Firewall (WAF):** Delivers static assets from edge locations and filters malicious traffic. It reduces unnecessary load on the application servers.

**Virtual waiting room:** Limits the number of users admitted to the purchase flow during a major sale. It assigns queue positions according to published rules and prevents uncontrolled bursts from overwhelming checkout and the database.

**Load balancer:** Distributes requests across multiple application-server instances and removes unhealthy instances from service.

**Application servers:** Implement authentication, event browsing, seat selection, hold creation, order management, and payment integration. Multiple stateless instances can scale horizontally.

**Cache:** Stores event descriptions, venue layouts, and other frequently accessed information. Seat availability requires a freshness strategy; cached seat status must never be used as the authority for a reservation.

**PostgreSQL primary:** Stores authoritative seat allocations, orders, payments, and ticket records. Transactions, row locks, foreign keys, and unique constraints protect data integrity.

**Read replica:** Handles suitable read-heavy queries, such as browsing event listings and historical ticket information. Reservation decisions and other consistency-sensitive operations use the primary database.

**Queue and background workers:** Handle tasks such as hold-expiration cleanup, ticket email delivery, and retrying transient notification failures. The queue smooths noncritical work during traffic spikes.

**Payment provider:** Processes payments without TicketHub storing raw card details. Signed webhooks and idempotent processing prevent duplicate confirmations.

**Backups and recovery:** Regular backups and tested restoration procedures help recover from data loss or database failures.

### 6.3 Surviving the Big Sale

During a major sale, TicketHub admits customers through the waiting room at a controlled rate rather than allowing all 200,000 customers to compete directly for database locks.

The CDN and cache serve event information and static content. Application servers scale horizontally, while the primary database remains the authority for seat allocation. Read replicas handle eligible read traffic, and background workers process notifications outside the checkout request.

The system should monitor queue length, API latency, database connection usage, lock waits, failed holds, payment errors, and available seats.

The sale rate should be adjusted based on load testing and database capacity. Increasing application-server count alone cannot fix a database bottleneck.

## 7. Trade-Offs

### Trade-Off 1: Strict consistency versus read performance

Using the primary relational database for all seat availability reads provides fresher results but increases load during a popular sale. Read replicas and caches improve performance but may return stale information.

**Decision:** Cache event metadata and use replicas for suitable browsing queries, but validate every hold against the primary database in a transaction. Slightly stale seat displays are acceptable if the final reservation check is authoritative and conflicts are handled clearly.

### Trade-Off 2: Fairness versus throughput

A virtual waiting room reduces sudden bursts and makes access more orderly, but it adds waiting time and can reduce the number of customers admitted per second.

**Decision:** Use a transparent queue with controlled admission. This sacrifices immediate access for more predictable system behavior and a fairer purchasing experience.

### Trade-Off 3: Seat-hold duration versus availability

Long holds give customers more time to complete checkout but leave seats unavailable to other buyers. Short holds increase availability but can frustrate users when payment takes longer than expected.

**Decision:** Start with a five-minute hold, display the expiration time clearly, and measure checkout completion and payment latency. Adjust the policy using evidence rather than guesswork.

### Trade-Off 4: Synchronous versus asynchronous work

Sending emails and generating other nonessential notifications during checkout simplifies the initial implementation but increases response latency and makes checkout depend on external services.

**Decision:** Commit the order and ticket records first, then use background jobs for notifications. Payment confirmation and seat allocation still require reliable state transitions and reconciliation.

## Conclusion

TicketHub is designed around three priorities: fast event browsing, fair access during major sales, and correct seat allocation. Caching, a waiting room, horizontal application scaling, and asynchronous background work help handle traffic spikes. Database transactions, row locks, and unique active-allocation constraints prevent two customers from purchasing the same seat. Payment idempotency and reconciliation ensure that external payment delays do not compromise ticket ownership.
